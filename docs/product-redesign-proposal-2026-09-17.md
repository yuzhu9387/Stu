## 1. 产品目标

帮助有孩子的家庭提前决定一周吃什么，把大部分准备工作集中到周末，并用好已经准备的食物。每天打开日历，就知道今天吃什么、从冰箱拿什么、还需要做什么。

主要解决三个问题：反复决定吃什么；备菜、烹饪和收拾占用太多时间；难以兼顾膳食搭配、孩子喜好和库存消耗。

核心闭环：

**周五生成下周草案 → 用户调整并确认 → 周末集中备餐 → 实际产出入库 → 每日按卡片准备三餐 → 完成后扣库存、记录喜好 → 影响下一周。**

本次设计以全家共同用餐、单独考虑宝宝需求为默认对象。用户确认继续采用本草案的默认口径；家庭设置仍允许调整用餐对象和份量。

## 2. 产品组织方式

| 方向 | 优点 | 代价 |
| --- | --- | --- |
| **日历为日常入口，Plan 为每周工作台（推荐）** | 今天做什么一眼可见；每周调整有集中空间；执行和计划自然衔接 | 必须明确草案与已确认版本的关系 |
| 保持聊天为首页 | 延续旧定位，适合自由输入 | 查看整周、找今天步骤、批量改餐仍要频繁查询 |
| 冰箱与备餐为首页 | 库存和批量制作突出 | 每天吃什么不够直接，规划流程分散 |

采用第一种。AI 嵌入计划和具体餐卡的上下文；菜谱和冰箱为整个流程提供数据。

## 3. 页面与职责

所有系统导航、按钮、表单、状态、错误提示使用英文。菜名、食材、tag、步骤、膳食指导和聊天内容允许中文、英文及混合内容，保留原文。

| 页面 | 核心职责 | 主要内容与操作 |
| --- | --- | --- |
| **Calendar**，默认首页 | 查看和执行一周三餐 | 七天 × Breakfast / Lunch / Dinner；Meal Card；餐食详情；Replace；完成、跳过、宝宝喜欢；右上角进入 Prep |
| **Plan**，独立页面 | 生成、讨论、调整和确认一周方案 | 本周 prompt；规划依据；周历；时间与搭配摘要；周末备餐方案；底部上下文聊天框；Confirm plan |
| **Prep** | 执行周末批量备餐 | 按类别分组的任务；推荐操作顺序；人工与经过时间；完成、跳过；实际份数入库 |
| **Fridge** | 查看和维护现有储备 | 名称、份数、类型；新增、增减、编辑、移除；本周预计使用和预计剩余 |
| **Recipes** | 收集并维护可实际烹饪的菜谱 | 文本/图片导入；食材、步骤、份量、时间；tag 管理；喜好状态 |
| **Settings → Planning guidance** | 管理长期规则 | 家庭人数与宝宝信息；饮食限制；可增补的膳食 skill；时间预算；周五生成时间与时区 |

现有购物清单保留为 Plan / Prep 中的辅助入口。Imports 合并进 Recipes 的导入状态与待检查列表。Lark、分享、账号与家庭功能保留已有能力，放在次级入口。通用 Todo 可保留为辅助记录；正式备餐需要专门的 Prep 数据和流程。

## 4. Calendar、Plan 与 Meal Card

### 4.1 一顿饭是一个组合

一个 Meal Card 对应某天的一顿饭，可以包含多个菜谱或食物组成，例如“鸡肉丸 + 米饭 + 西兰花”。一份预制菜不能被默认为完整的一餐。

卡片摘要展示餐名、菜品组合、份数、当天人工准备时间，以及 From fridge / Fresh / Mixed 等来源提示。详细信息在卡片打开后展示，避免日历过密。

详情包含：

- 需要从冰箱取出的具体食物和份数。
- 已在周末完成的步骤、当天剩余步骤、必要的提前准备。
- 各部分菜谱、人工时间、等待时间和上桌预计耗时。
- Replace，可替换一个组成部分或整顿饭。
- Reference in chat，将稳定的日期、餐次、餐卡标识带入 Plan 聊天。

日历始终显示七天三餐，包括空餐位。支持修改餐次、日期、组成和份数，也支持标记在外就餐等无需在家准备的餐次。

### 4.2 同步与确认边界

Calendar 和 Plan 是同一周计划的两个视图，共用餐卡标识、数据与版本。

- 周五自动生成的是 **Draft**，写入并保存草案，等待用户调整。
- 同一草案在两个页面查看时即时同步；Calendar 中明确标记 Draft，不将其当作已经确认的执行安排。
- 点击 **Confirm plan** 后，确认版本成为日常执行依据，同时确定备餐清单与库存分配。
- 已确认计划可以有后续修改草案；在应用修改前，执行视图仍展示当前确认版本。
- 编辑始终作用于当前所见版本：在 Draft 中保存只更新该草案；在已确认版本中明确选择替换或手动保存时，直接更新该确认版本并同步 Plan，显示变更摘要和 Undo。
- 已确认版本与修改草案同时存在时，界面明确标出当前版本，用户可切换；从草案进入执行需要 Confirm plan / Apply changes。确认版本发生新修改后，未应用草案先检查并合并差异，不能覆盖较新的手动变更。
- 批量 AI 调整先展示受影响餐次与差异，再一次应用。已完成的餐食保持历史记录，默认只调整未执行餐次。
- 更换餐食同步重算备餐、库存分配、采购缺口、时间和搭配；如果库存或计划已被另一处修改，先刷新受影响结果。

草案、确认和执行状态相互独立；生成计划不代表已经做饭。

## 5. Planning Agent

### 5.1 每次规划输入

1. 冰箱真实剩余份数，以及已被当前计划分配的份数。
2. 预计本周余下餐食还会消耗多少，推算下周开始时的库存；预计值与实存分开。
3. 已启用的膳食指导 skill，以及家庭人数、宝宝年龄、过敏与饮食限制。
4. 本周 prompt，例如“优先用掉菠菜”“周三要特别省事”“想换几种早餐”。
5. 菜谱库：组成、份量、步骤、tag、时间、是否适合批量准备、家庭喜好。
6. 上周实际吃过的餐食；没有执行记录时参考已确认计划，并标明历史不完整。
7. 周末备餐时间、每日时间预算、可用厨具和人员。

本周 prompt 默认只作用于目标周。只有用户明确要求长期记住，才更新偏好或 guidance。

### 5.2 决策规则

先满足显式饮食限制、供应数量和时间预算，再综合食物搭配、旧库存优先使用、宝宝喜欢、减少重复和引入新菜。

- “消耗老的”优先考虑入库较早、用户标记需要优先使用的食物；不能超过实际或可实现的预计份数。
- “稳定做新的”通过每周少量新菜形成节奏；草案默认目标为 **2 道新菜/周**，用户可修改。可优先尝试菜谱库中尚未做过的菜，不等同于必须让 AI 凭空生成。
- 为减少重复，比较具体菜谱与搭配，不只是比较菜名；宝宝喜欢可以增加权重，但不覆盖限制和时间预算。
- 允许合理复用同一批备餐，例如肉丸分别搭米饭和面；避免整周照抄，也避免为了完全不重复而增加大量劳动。
- 新生成菜谱必须有足够的食材、份量、完整步骤和时间估算，才能作为可执行计划的一部分；仅有菜名不能确认成可执行餐食。
- 多道菜的操作由排程计算验证；模型的文字承诺不能代替时间、份数和依赖检查。
- 如无法满足全部条件，展示具体冲突和最少的调整选择，保留已可行部分；不会将不满足预算的计划标成符合要求。

输出包括：七天三餐日历、周末 Prep 方案、每天剩余工作时间、库存使用与预计剩余、简明搭配说明、必要采购项、新菜与重复情况。

### 5.3 可随时增补的膳食 skill

Settings 中可新增、编辑、启用、停用和删除 guidance。支持自然语言文字和文档内容，记录名称、内容、适用对象、来源与版本。

用户可以用中文写规则；AI 在规划前说明采用了哪些规则。每份计划记录其采用的 guidance 版本，方便解释和重算。修改规则不会静默改变已经确认的餐食；下一次规划使用新版本，当前周可主动重新检查。

食物分组与搭配规则应来自已启用 guidance。缺失的营养数据展示为未知，不用 tag 或菜名推导伪精确营养数值。本轮不规定具体儿童营养摄入标准。

## 6. Plan 聊天的修改行为

聊天框位于 Plan 页面下方；可以选择一张或多张卡片加入上下文，也可以直接输入。

Agent 依次识别：**意图 → 引用对象 → 修改范围 → 不满意原因 → 希望的结果 → 受影响的关联内容**。

| 用户输入 | 应识别的范围 | 处理 |
| --- | --- | --- |
| 引用周三 Dinner：“换个不用开火的” | 这一顿饭 | 推荐可用库存组成，只改选中的餐次 |
| “这周早餐太重复了” | 目标周所有早餐 | 保留午晚餐，调整早餐多样性 |
| “只换这里的蔬菜” | 所选餐卡的蔬菜组成 | 保留蛋白质和主食 |
| “周末只能准备两小时” | 备餐及依赖它的未执行餐次 | 重算受影响范围，说明哪些餐因此需要变化 |
| 引用晚餐却说“早餐全换了” | 引用和文字冲突 | 先确认范围，不猜测并直接批量覆盖 |
| “宝宝不喜欢这个口感，以后别推荐” | 本次餐食 + 持久偏好 | 记录原因并调整未来推荐；说明保存了长期偏好 |

范围明确时直接更新草案，给出可撤销差异，不反复询问。若必须扩大范围，则解释关联影响后让用户选择是否应用。用户可锁定满意的餐食，重规划默认保留这些餐次。

## 7. 时间模型与备餐约束

### 7.1 三个数值分别显示

- **Active time**：需要人参与的备料、实际操作、分装和收拾时间。
- **Waiting time**：无需持续参与的等待片段，例如炖煮、发酵。
- **Elapsed time**：从开始到目标完成的真实经过时间，考虑步骤先后、人员及设备占用。

单道线性流程可以是 Total 90 min / Active 30 min / Waiting 60 min；步骤有重叠时，Total 应按步骤排程计算，不能一律用两个字段相加。

### 7.2 多道菜的计算

暂定一位主要操作者。人工片段不能互相重叠；等待期间可以准备其他菜。烤箱、灶台等同一资源的冲突和步骤依赖必须计入。

例如，A 菜在 0–30 分钟操作，30–90 分钟等待；B 菜在 30–50 分钟操作，50–60 分钟等待，且两者设备不冲突。此时人工工作 50 分钟，整批完成耗时 90 分钟。

**总耗时取实际排程中最后完成任务的结束时间。** 完全可并行时可能等于最慢一道菜的时长；有人员、设备或先后依赖时，会超过最长单菜时长，不能直接取所有单菜时长的最大值。

### 7.3 本轮建议采用的预算

- “半天”暂按 **4 小时**。普通周末备餐从开始到分装收拾完成的经过时间 ≤ 4 小时，同时显示人工总时长。
- 烘焙、发酵等可无人照看的延长等待单独列出，不计入上述普通备餐窗口；揉面、整形、进出炉和收拾等人工操作仍计入。需要回来处理的时点要清楚显示。
- 若烘焙占用同一设备导致普通备餐延后，该冲突必须计入普通备餐排程；属于关键依赖的等待不能隐藏。
- 按用户“每天”的表述，**三餐人工操作合计 ≤ 30 分钟/天**，暂包括准备、烹饪、装盘与收拾。用餐本身不计入。
- 每顿饭同时显示真实上桌耗时，明确提前解冻等依赖；不会用“只需操作 5 分钟”掩盖一小时后才能吃。
- 所有时间估算可修改；低置信度时间需标记。计划需留出适当余量，不能把 AI 估算描述成已测得的实际时间。

## 8. Prep 页面

Calendar 右上角的 Prep 按钮进入所选周计划的备餐页。Plan 同时展示该周末的备餐预览。

默认分组：**Baking / Vegetables / Protein / Carbs / Other**。Protein 包括肉、鱼、蛋、豆制品等；具体命名在 UI/UX 阶段确认。

分类便于找任务，推荐操作顺序负责跨类别并行安排。不能为了按类别显示而让用户先做完全部肉类再做全部蔬菜。

每个备餐项包括关联菜谱、计划产出份数、用于哪些餐、人工与等待片段、必要工具、具体步骤、小型 ✓ / × 操作。页面汇总预计结束时间、人工工作量和剩余任务。

- ✓ 完成：默认实际产出等于计划份数，可快速修改实际份数，完成最终可储存产物时入库。
- × 没做：不增加库存，找出受影响餐次并给出局部替代方案。
- 洗菜、切配等中间步骤可以完成，但不能每完成一步就重复生成完整成品库存。
- 分批完成可以按实际产出入库；重复点击和页面重试不会重复入账。
- 烘焙等待有独立时间提示，需等待最终完成才记成品入库。
- 完成后可继续用快速表单添加额外做出的食物。

## 9. Fridge 与执行状态

### 9.1 简单录入，可靠计算

必填只保留 **Name / Portions / Type**。支持中文名称、小数份数、手动增减和纠正。Type 以 Protein / Carbs / Vegetables 为基础，提供 Other 容纳无法归入前三类的食物。

可选项包括菜谱关联、Raw / Prepared、Fridge / Freezer、制作或入库日期、优先使用、用户填写的使用期限。入库时间可自动生成；不强迫用户维护复杂仓储字段。

简单录入默认使用“家庭标准份”作为数量单位，由家庭设置一次，之后每个条目自动继承，不增加逐条必填字段。它用于库存与餐次间分配，不自动等同于固定克重或某种营养量；计划中的需求份数可以直接修改。

从菜谱备餐入库时默认沿用该菜谱已明确的产出份量，并记录与家庭标准份的关系。用户可选成人份、宝宝份等覆盖默认基准；不同基准只有换算明确时才自动互相分配，否则使用同基准库存或提示需要补充。不能把人数直接当作精确营养份量。

预制菜按份数参与分配。原材料数量不明确时可以记录“本周优先消耗菠菜”这样的提示，但不能据此承诺足够供应某几顿饭。不会把“1 份”擅自换算成克数并生成精确购物量。

### 9.2 计划分配与实际库存分开

- 规划时分配现有库存，也可以引用某个尚未完成的 Prep 预计产物；二者来源要区分。
- 确认计划仅确定预计用途，不立即增减实存。
- Prep 完成后记录真实产出，再匹配到已计划的用途。少做了几份时，标记受影响的餐次需要调整。
- 若 Prep 使用已记录的原料或已有储备，在记录真实产出时同步扣减实际投入；数量不明确的原料只保留消耗提示，不虚构精确扣减。原料扣减、成品增加是同一次可追溯变动，防止原料和成品同时被重复分配。
- 用餐 ✓ 完成后，扣除该餐实际用到的库存份数；做出可保留的新储备时可顺手记录剩余份数。
- 吃预制菜只扣其成品份数，不再次扣除已在 Prep 消耗的原料。做了但未吃完仍按实际用料记录，通过剩余入库处理；不能用“没做”撤回已经发生的消耗。
- 用餐 × 没做后，不扣库存，释放这顿饭的分配。
- 手动修改库存后，立即重新检查未来餐食是否仍有足够供应。
- 撤销完成会撤销对应库存流水；如果该批库存已经被后续使用，解释受影响数量并引导纠正，不造成重复加减或负库存。

### 9.3 完成与喜好是不同状态

执行状态：**Planned / Completed / Skipped**，分别对应默认、小对勾和小叉叉；可撤销。没有点过和明确没做分开记录。

宝宝图标代表 **Baby liked it**，数据库使用 boolean。点击设为 true，再点取消；false 表示“没有被标记为喜欢”，不解释成“讨厌”。不喜欢的原因通过聊天单独记录。

该标记独立于完成状态，不会扣库存。Meal Card 的标记记录在本次整餐体验；单菜喜欢记录关联到具体菜谱。多菜组合整体被喜欢时，不自动断言其中每一道菜都被宝宝喜欢；以后优先推荐该组合，用户也可以在详情标记具体菜谱。

Prep 中可储存成品也提供宝宝图标，适用于实际试吃反馈；洗菜、切菜等中间任务不显示喜好操作。

## 10. Recipe 导入、tag 与时间

首轮必须完成可真实使用的文本和图片导入，支持一次输入包含多个菜谱。保留原文或原图，AI 生成可编辑的食材、份量和步骤；解析失败保留来源，方便修正或重试。

每份菜谱需具有：

- 名称、食材、可产出份数、准备/烹饪/保存后使用的步骤。
- 总耗时、人工耗时；可展开查看等待片段与步骤依赖。
- 适用餐次、适合批量制作与否，以及可供规划使用的组成信息。
- 自定义 tag，例如 小孩饭、Breakfast、Protein、Carbs；可创建、重命名、合并、删除并批量应用。
- 已做过与宝宝喜欢的历史，原始来源和手动修改。

tag 的文本由用户自由管理；tag 与可计算的食物组成、时间和份量保持区分。删除一个 tag 不删除菜谱或库存。

AI 识别时间属于估算，可由用户修改；编辑步骤或产出份数后重新检查时间。不把现有 prep_minutes / cook_minutes 直接当成“人工/等待”的可靠区分。

现有链接和 Excel 导入继续保留为扩展能力，准确展示其可用状态，不用占位接口冒充支持。

## 11. 周五自动规划

自动规划由应用自己的定时任务执行，不是为当前 Codex 对话创建提醒。固定生成家庭本地时区的下一个周一到周日，以及此前周末的备餐方案。

暂定周五 17:00，时间、时区和备餐日可修改；默认备餐日为周日。用户可以提前填写下周 prompt，周五取最新输入生成。错过填写也能在草案里继续调整。

- 同一周重复调度不创建多份冲突计划。
- 已有用户修改过的草案或已确认计划时，保留用户工作，提供待更新提示或新的建议差异。
- 草案保存后显示站内待确认提示。不会因定时任务到达而自动确认。
- 服务恢复后补做遗漏生成；失败显示可重试状态，保留当前日历。
- 周五至周末库存可能变化，用户确认时及 Prep 开始前重新检查。

## 12. 数据库 MCP

提供一个外部 AI 可以连接的 MCP 层，读取业务数据与结构，并能按用户指令创建、修改、删除数据。能力覆盖菜谱、tag、周计划、餐卡、备餐、冰箱、反馈和膳食指导，而不局限于固定问答。

支持直接完成“冰箱里的鸡肉丸改成三份”“查询上周早餐”“把这一餐换到周四”等操作。查询、普通修改不需要每次重新确认。

推荐 MCP 复用应用的数据操作逻辑：修改完成状态时同步库存流水，修改餐卡时同步计划与备餐。这样外部 AI 的操作与 UI 结果一致，并且可追溯、可纠正。这个原则不限制 AI 的业务读写能力；原始 SQL 或通用数据库工具的具体接口在后续 spec 决定。

访问范围是已连接用户有权操作的家庭数据。计划确认状态可被明确的“确认这个计划”指令修改；自动规划和普通修改不会默认为用户已确认。保留原有登录、家庭隔离和记录归属。

## 13. 本轮范围与旧功能处置

必须形成完整闭环：Calendar、Plan 与上下文聊天、Prep 排程与执行、Fridge、Recipe 文本/图片导入和 tags、膳食 guidance、周五自动草案、英文 UI 与中文内容、MCP。

保留并复用：账号与家庭、现有菜谱数据、计划 CRUD、AI 调用与任务基础、采购聚合、来源保留、原有分享和 Lark 接口。分享传播、Lark 新交互、Excel 等不作为本次核心页面重设计的主线。

旧计划和菜谱需要保留。缺失时间、份量和组成等字段的旧菜谱可以继续查看编辑，但不能被默认为已验证满足新规划约束。历史计划没有真实执行数据，迁移时不自动标成吃过。

## 14. 后续 demo 需要验证的完整故事

1. 粘贴中文菜谱并上传图片，查看生成步骤和两种时间，编辑与管理 tag。
2. 冰箱已有旧储备，输入本周偏好，查看营养指导和下周草案。
3. 在 Plan 引用周三晚餐，提出修改原因，只调整指定范围并显示关联变化。
4. 确认草案，打开 Calendar，验证餐卡、日期和组成同步。
5. 从日历右上角进入 Prep，检查分类与并行顺序；一项少做、一项跳过，库存及受影响餐次同步变化。
6. 执行一餐，点击 ✓ 和宝宝图标；另一餐点击 ×；核对库存与喜欢状态，并测试撤销。
7. 手动纠正库存，查看未来缺口，局部替换一餐。
8. 展示下周生成如何参考旧库存、上周实际吃过与宝宝喜欢；演示无法满足时间预算时的状态。
9. 用演示数据模拟周五生成、失败重试、中文内容和 MCP 修改同步。静态或本地 demo 中清楚区分模拟与真实后端能力。

成功依据：每天可直接按计划执行；普通备餐窗口满足半天限制；每天人工时间满足预算；库存账和执行记录一致；局部修改没有意外改动其他餐；推荐能解释规则、库存和历史依据。
