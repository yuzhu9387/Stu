# Stu 页面设计与交互 Prompt

以下内容可直接复制给 UI/UX 设计或前端原型 AI。

---

你是一名资深产品设计师和前端原型工程师。请为 Stu / Family Table 设计一个页面互相联动的家庭餐食规划应用，并制作可点击的多页面前端 demo，供用户确认页面、功能和交互。此阶段使用共享的模拟数据，生产数据库、真实 AI、定时任务和 MCP 接入在后续 spec 阶段实施。

## 产品目标

帮助有孩子的家庭减少每天决定吃什么、准备食物和收拾的时间，同时兼顾食物搭配、宝宝喜好、旧库存消耗和少量新菜。

核心流程：周五生成下周草案 → 用户调整确认 → 周末集中备餐 → 实际产出入库 → 每天按餐卡执行 → 扣减库存并记录宝宝喜好 → 影响下一周计划。

默认全家共同用餐，单独考虑宝宝需求；普通周末备餐经过时间不超过 4 小时，每天三餐人工操作合计不超过 30 分钟，包含分装和收拾。每周新菜目标默认为 2 道，可修改。

## 设计基调与共同规则

- 所有导航、按钮、状态、表单和错误提示使用英文。菜名、食材、步骤、tag、膳食指导和聊天内容支持中文、英文及混合文本，保留原文。
- 沿用温暖米白、鼠尾草绿、深绿文字、克制的陶土色强调色。界面清晰、平静，优先让人看懂今天要做什么。若附有选定的视觉参考，以该参考为准。
- 桌面方便完整浏览一周；移动端通过周导航和日期选择展示单日三餐，保留同样操作。
- 每页有明确的主任务。常用小操作用图标，配 tooltip、可访问名称和足够点击区域。不要把主要信息挤进大量装饰面板。
- 所有页面共享同一份数据；切页不丢失选择、修改、草案或执行状态。显示成功前完成对应状态变更；失败保留用户输入。

## 一、页面结构和跳转关系

主要导航为 Calendar、Plan、Fridge、Recipes；Settings 为次级入口，Planning guidance 位于 Settings 内。

| 起点与操作 | 目标 | 必须保留的上下文 |
| --- | --- | --- |
| Calendar → Review / Edit plan | Plan | 所选周、计划、当前版本 |
| Calendar 餐卡 → Reference in chat | Plan 底部聊天框 | 所选周、日期、餐次、餐卡以及所选食物组成；自动添加引用 chip，不自动发送消息 |
| Calendar 右上角 → Prep | 对应周的 Prep | 同一计划与版本；默认对应该周之前的周末 |
| Plan → Preview prep | Prep | 草案模式只预览；确认版可以执行 |
| Prep → View in fridge | Fridge 对应食物或批次 | 刚产出的库存项；返回后保持原备餐进度 |
| Fridge → View planned meals | Calendar 或 Plan 中的相关餐卡 | 对应周和版本，聚焦受影响餐次 |
| Meal details / Prep → View recipe | Recipe detail | 精确菜谱；返回原餐卡或任务，不重置页面 |
| Plan → Manage guidance | Settings → Planning guidance | 返回原周计划，保留 prompt 和聊天内容 |

购物清单作为 Plan / Prep 的辅助入口；导入状态放在 Recipes 中。不要让用户离开当前任务后找不到回来的位置。

## 二、共享 Meal Card 与餐食详情

Calendar 和 Plan 使用同一个 Meal Card。一个卡片代表一天中的一顿饭，可以包含多个组成，例如“鸡肉丸 + 糙米饭 + 西兰花”，不能把一份预制菜当作完整一餐。

卡片展示：餐次、菜品组合、份数、当天 Active time、From fridge / Fresh / Mixed、必要状态。点击打开详情：桌面可用侧面抽屉，移动端使用适合窄屏的详情层。

详情展示：从冰箱取出的食物与份数、已经在周末完成的步骤、今天剩余步骤、提前解冻等依赖、各组成的菜谱、Active / Waiting / Elapsed time。

操作包括 Replace、Reference in chat、编辑日期/餐次/份数、Lock meal，以及执行状态和宝宝喜欢。

- Replace 先明确范围为一个组成或整餐，再给出候选及时间、库存、备餐影响。选定后只更新该范围，提供 Undo。
- Calendar 的确认版餐卡提供小型 ✓ Mark completed、× Skip、宝宝图标 Baby liked it。草案中执行操作不启用，避免将规划当作实际制作。
- 执行状态为 Planned / Completed / Skipped；未操作和明确跳过必须区分。完成和跳过互斥，重复点击不重复记账。
- Baby liked it 是独立 boolean；false 表示没有被标记为喜欢，不代表讨厌。点击喜欢不改变执行状态或库存。
- 整餐喜欢不自动等于喜欢其中每道菜；详情允许对具体菜谱单独标记。

## 三、Calendar：日常查看与执行

默认首页。始终展示七天 × Breakfast / Lunch / Dinner，包括空餐位。支持切周、回到今天、添加或修改餐食，以及外食等不需要在家准备的安排。

清楚标记当前查看的是 Draft 还是 Confirmed。优先突出今天和需要处理的餐次，而不是用密集警告打断所有餐卡。每天下方显示三餐人工时间合计；超过预算时可直接进入 Plan 调整当天。

完成一餐后，卡片显示 Completed，并更新 Fridge、计划剩余用量和历史。跳过后保留记录、释放该餐的库存分配但不扣实存。提供撤销；若撤销影响已有后续消耗，展示冲突而非产生负库存。

## 四、Plan：每周规划和上下文聊天

Plan 是独立工作台。页面上方是目标周、本周 prompt 和生成/确认操作；中部是同一套周历；周历后展示简明的食物搭配、时间、库存使用和周末 Prep 摘要；聊天框位于页面下方。

规划综合读取：真实库存和已分配份数、预计到下周开始时的余量、膳食 guidance、家庭条件与限制、本周 prompt、完整菜谱库、上周实际吃过什么、宝宝喜欢、时间和设备条件。

允许合理复用同一批备餐，优先消耗较老储备，安排少量新菜；喜欢的饭提高权重，但不覆盖限制和预算。新菜必须有完整可执行菜谱。数据不足或条件冲突时明确说明，不伪造营养数值或合规时间。

### 计划版本

- 生成结果保存为 Draft。Confirm plan 后成为执行依据，但不立即增减库存。
- 编辑当前所见版本：Draft 中保存只改草案；确认版中明确手动保存或选择替换，则应用该修改并同步另一页面，显示摘要和 Undo。
- 确认版和后续修改草案可以并存，必须明确区分。Apply changes 后才将修改草案用于执行。
- 确认版已经发生新的修改时，旧草案先检查差异，不能直接覆盖。
- 默认保留已完成历史和用户锁定的餐次。

### 聊天行为

用户可选一张或多张卡片加入引用，也可直接输入。引用 chip 显示日期、餐次和必要的组成信息，可移除。

Agent 按“意图 → 引用对象 → 修改范围 → 不满意原因 → 期待结果 → 关联影响”处理。用简短结果说明范围，不展示内部推理过程。

- “只把周三晚餐的蔬菜换成冰箱里的西兰花”：仅改该组成。
- “这周早餐太重复”：只调整早餐，保留午晚餐。
- “周末只能准备两小时”：重算备餐及依赖它的未执行餐次，并显示扩大影响的原因。
- 引用了晚餐却说“早餐全部换掉”：先澄清范围。
- “这个口感宝宝不喜欢，以后不要推荐”：明确记录长期偏好；普通本周 prompt 默认不持久化为长期规则。

范围明确的单项修改直接更新草案并可撤销；批量修改展示受影响餐次和 Before / After 后一次应用。不要每说一句就重做整周。任何替换同步重算 Prep、库存分配、采购缺口、时间和食物搭配。

## 五、Prep：集中备餐与实际产出

从 Calendar 右上角或 Plan 进入。分类为 Baking、Vegetables、Protein、Carbs、Other，同时提供推荐执行顺序；分类不能强迫按类别串行完成。

任务展示：做什么、产出几份、用于哪些餐、相关菜谱、步骤、Active / Waiting / Elapsed time、所需设备、小型 ✓ / ×。整页显示人工总时长、预计结束时间和剩余任务。

- 点击完成时可快速修改 Actual portions，默认等于计划份数；真实成品完成后入库。
- 洗菜、切菜等中间步骤完成不会重复增加成品库存。
- 使用已记录原料时，同步扣减实际投入并增加成品；数量不明时不编造精确扣减。
- 实际少做或跳过，显示具体受影响餐次及缺口，支持跳转去调整。不能暗中减少食用份数。
- 分批产出可分批记录；重复提交不重复入库。
- 可储存成品支持试吃后的 Baby liked it；普通中间任务不显示该操作。
- 完成后可以直接添加额外做出的食物，并进入 Fridge 查看。

时间口径：人工时间包含需要人参与的操作和收拾；无人等待可并行利用。整批 Elapsed 按步骤依赖、人员和设备排程后的最晚完成时点计算，不能简单相加或一律取单菜最大值。烘焙/发酵可无人照看的延长等待单列，人工操作和影响普通备餐的设备冲突仍计入。

## 六、Fridge：简单维护，清楚显示用途

新增必填仅 Name / Portions / Type，支持小数份数及中文。Type 为 Protein / Carbs / Vegetables / Other。提供增减、编辑、移除；高级信息如存放位置、Raw / Prepared、入库日期、使用期限、菜谱关联为可选项。

每项区分 On hand、Planned use、Expected remaining；预计 Prep 产出不能冒充实存。份量沿用家庭默认基准，不同基准不擅自换算。

编辑库存后同步检查未来餐食。存在缺口时列出受影响的日期和餐次，提供 View meal / Adjust plan，避免让用户自行查找。完成用餐扣成品，不再次扣已经在 Prep 用掉的原料；喜欢和计划确认都不扣库存。

## 七、Recipes 与 Planning guidance

Recipes 提供搜索、餐型/tag 筛选、菜谱详情、编辑和新增。文本/图片导入流程为选择输入 → 解析中 → 预览并修正名称、食材、份量、步骤和时间 → 保存；支持一次输入多份菜谱，失败保留原始内容并可重试。

菜谱明确显示 Total / Active time，详情可展开等待片段与步骤依赖。AI 时间标为估算且可修改。tag 可创建、重命名、合并、删除和批量应用，删除 tag 不删除菜谱。菜谱已被计划引用时，修改后提示哪些未执行餐次需要重新检查；不改写已经完成的历史。

Planning guidance 可增改、启停和删除膳食 skill，支持中文规则、来源、适用对象和版本；同时管理家庭条件、时间预算、每周新菜数量、家庭时区与周五自动生成时间。默认周五 17:00 生成下周草案、周日备餐。

更新 guidance 影响下次规划；当前周通过主动重新检查应用，不能静默改动已确认餐食。周五重复触发不覆盖用户已修改的草案或确认版；展示生成中、待确认、失败重试等状态。

MCP 属于后台接入能力。前端只需保证外部修改也能刷新相关页面并保持相同联动规则；不要创建数据库管理主页面。模拟 MCP 更新时明确标注 Demo，不声称已真实连接。

## 八、用同一套数据演示跨页流程

固定示例周为 Sep 21–27, 2026，周末备餐 Sep 20。初始库存：鸡肉丸 2 份、熟糙米饭 6 份、西兰花 4 份。周三与周五晚餐各需要 3 份肉丸。其他餐食不消耗这三项示例库存。

1. Calendar 打开周三晚餐“鸡肉丸 + 糙米饭 + 胡萝卜”，引用到 Plan。
2. 聊天要求只将胡萝卜换成库存西兰花。只改该组成，保留周三餐卡和其余餐次。
3. Confirm plan；库存仍为 2 / 6 / 4。
4. Prep 中鸡肉丸计划做 6 份，实际只做 3 份；库存变为 5 / 6 / 4，周五晚餐提示缺 1 份。
5. Fridge 查看实存、预计用途、缺口和受影响餐次。
6. 完成周三晚餐，肉丸、米饭、西兰花各扣 3 份；库存为 2 / 3 / 1。
7. 点击 Baby liked it，库存不变；Undo complete 后恢复到 5 / 6 / 4，喜欢状态保留。
8. 演示 Skip 不扣实存，以及手动纠正数量后相关餐次的缺口提示。

未来日期的执行需清楚标明模拟场景。每餐 Active 与当天合计必须算得一致；不得照抄视觉稿中未经核对的示例数字。

## 交付与验收

交付页面关系图、每页主要布局和交互说明，以及共享模拟状态的可点击 demo。覆盖正常、空白、加载、失败、库存不足、超时预算、范围歧义、Draft / Confirmed 和 Undo 状态；核心按钮、输入框、筛选、导航和弹层需实际可用。

验收重点是：从一张餐卡出发可以调整计划、查看备餐、更新库存、完成用餐并返回原位置；各页始终显示一致的周、版本、餐次和份数；局部修改不意外重做其他餐次。AI、图片解析、定时和 MCP 如为模拟，清楚标识其边界。

完成 demo 后等待用户确认页面、功能和交互，再编写生产 spec 并实施。
